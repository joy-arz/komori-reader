# Source metadata, sessions and app follow-up — October 15, 2026

Baseline: `202f2d3`. This review accompanies 0.6.0-alpha.1. It supersedes affected findings in APP_AUDIT_2026-10-15.md; the earlier document describes an older revision and is not a statement of current defects.

## Root causes and delivered changes

- **Missing authors:** gallery detail adapters never assigned `creatorsJson`. Both HentaiZap and Nhentai now parse author/artist metadata links, retain source-scoped identifiers, expose Follow locally, and browse the creator's original source. Nhentai tags previously appeared only in description text; both sources now persist structured, tappable tags.
- **Creator search switched sources:** ReaderViewModel unconditionally switched every creator search to MangaDex. Routing now derives the source from the creator ID. MangaDex UUIDs remain compatible. Sorting and pagination retain the creator selection.
- **Author follows were buried:** Authors is now a separate bottom-navigation destination with name filtering, source/role labels, browse and unfollow. Follows remain local; this release does not schedule creator update notifications.
- **Metadata search:** Title, Tag and Author search modes are available for gallery sources. Tag/Author entry resolves an exact source slug; this is not a fuzzy creator directory search. Tapping metadata uses the actual source-returned path. Nhentai title search also retains selected tag terms and popularity on later pages. HentaiZap category filtering remains distinct from metadata tags.
- **Sorting:** HentaiZap retains its source-native Popular, Top Rated and Downloaded options. Nhentai now offers daily, weekly, monthly and all-time popularity. No fabricated view counts or client-side ranking of a single page is used.
- **HTTP 403 sessions:** the native client had no cookie jar or in-app verification flow. Verify source opens a visible, user-operated WebView. Native requests, covers and verification use the same session user agent and Android CookieManager. Cover requests also carry their source Referer for normal hotlink checks. CookieManager performs domain/path/expiry handling; the native bridge restricts cookies to HTTPS source hosts and never forwards them to unrelated CDNs. Reset sessions deliberately clears all source browser sessions and web storage, with confirmation, retaining library/download data.
- **Failure handling:** explicit verification challenges are distinct from plain HTTP 403 and rate limiting. Source access failures stop automatic reader/next-chapter retries and place downloads in Verification required. Verify, then resume downloads explicitly. Returning from verification retries native access; page-load completion is not treated as proof of access.
- **Comix:** removed from registry/default order/UI; old saved source-order strings discard it without resetting other preferences or deleting library data.
- **Additional fixes:** opening a browse card no longer overwrites richer cached metadata before a network refresh; failed metadata refreshes are visible; canceled source/MangaDex catalog calls cancel their actual sockets; continuous-reader next loading now observes changed next-chapter identity.
- **Migration:** Room 4 → 5 adds `manga.tagsJson` with an empty-array default. Existing titles, creator follows, preferences, downloads and reading progress remain intact. Exported schema is committed.

## Validation and limits

Deterministic JVM coverage includes metadata parsing, duplicate/count removal, unrelated-link rejection, source-scoped creator IDs, metadata route encoding, pagination/sort retention, tag catalog parsing, plain HTTP 403 versus verification, cookie host isolation, removed-source preferences and socket cancellation. Android instrumentation covers the actual CookieManager bridge, cookie path/HTTPS isolation and Room migrations, alongside the existing reader tests. Exact final results are recorded in VALIDATION.md.

New metadata fixtures are synthetic structural examples, not a claim that every current source layout has been captured. Direct live requests to both HentaiZap and Nhentai returned HTTP 403 on the validation network. Search-index snapshots confirmed HentaiZap's artist directory and popularity destination, but cannot substitute for native-device validation. Live tag/author results, popularity ordering and challenge completion require a compatible source session on the user's network. Optional live smoke tests are not part of the deterministic result.

An ordinary HTTP 403 can reflect network policy, regional restrictions or a site denying native access. Cookie sharing cannot guarantee access, and some challenge providers reject embedded WebViews. The verification screen has no JavaScript bridge, disallows file/content access and mixed content, restricts navigation, and uses default TLS validation. No automated challenge solving is implemented. Cookies and authorization values are not written to diagnostic logs. App backup remains disabled.

Android references: [CookieManager](https://developer.android.com/reference/android/webkit/CookieManager), [WebViewClient](https://developer.android.com/reference/android/webkit/WebViewClient), [Cloudflare challenge detection](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/).

## Remaining app improvements, in priority order

1. **User-controlled metadata backup/restore.** Library, follows, preferences and progress still have no export/import workflow. Add a versioned document-picker backup with preview, strict validation and transactional restore. Exclude sessions and image files by default. Gate with clean-install round trips and malformed-file rejection.
2. **Download worker ownership and deletion coordination.** Images and catalog calls now cancel their sockets, and image transfers are bounded and validated. However, pause/delete still rely on WorkManager cancellation acknowledgement before changing/deleting local state. Serialize worker publication and deletion per chapter and verify active ownership before progress/completion updates. Test pause/delete during a slow transfer and manifest resolution. Do not mistake the older audit's already-fixed transfer limits for outstanding work.
3. **Durable queue and waiting states.** Jobs are serialized by an in-process mutex, with no persisted queue position. Add ordering and explicit waiting-for-Wi-Fi/storage states, then test hundreds of jobs across process death. Verification required is implemented; it is separate from transient network retries.
4. **Bidirectional continuous reading.** The bounded window appends forward and discards older chapters, but does not reload previous neighbors at the top boundary. Add prepend with stable scroll anchoring. Next-chapter identity invalidation is fixed in this patch. Test forward five/back four, rotation and feed refresh.
5. **Complete failure-aware retry policy.** Verification/access failures now need user action. Offline, HTTP 429/Retry-After, missing content and low storage still need distinct scheduling rules. Visible-image attempt budgets remain tied to composition lifetime. Introduce typed page-level state and a stable attempt budget, with fake-clock and network tests.
6. **Process-death navigation.** Reading progress is persisted, but selected title, active source/filter and current reader screen primarily live in ViewModel state. Persist navigation identifiers with SavedStateHandle and rebuild from Room. Never persist transient activity objects or session credentials in saved UI state.
7. **Large-library performance.** Whole-table manga/progress/download flows and repeated list scans remain. Benchmark 1,000 saved titles and 50,000 progress rows before introducing indexed projections/paging. Use maps for repeated lookups. Verify on a physical low-memory phone; emulator memory samples are not a performance guarantee.
8. **Release/device gates.** Add API 26/API 36 instrumentation, in-place signed upgrade tests, accessibility/large-font checks and interrupted-download cases to CI. Local API 30 checks supplement current CI's JVM/lint/build gates. Add Stable/Preview updater channels, conditional requests and a longer check cooldown.
9. **Product polish.** Categories, unread badges, a title-update feed, chapter jumps, webtoon zoom and storage-management totals remain useful additions. Implement after backup/queue reliability and measure with real libraries.

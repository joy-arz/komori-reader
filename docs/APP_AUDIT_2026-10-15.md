Reviewed revision: `53f1e09` (also the GitHub main HEAD when checked). This is a code, architecture and test review, not a new full device walkthrough or penetration test. No app behavior was changed during this review.

Validation: forced a fresh JVM test execution with `cleanTestDebugUnitTest testDebugUnitTest`: 55 tests, 51 passed, 4 optional live tests skipped, zero failures/errors. `lintDebug` succeeds with 17 warnings and no errors; lint reused unchanged analysis outputs. The six Android instrumentation tests and signed upgrade checks documented in VALIDATION.md were performed in the previous release pass, not rerun here. ## Prioritized findings

### 1. Browser verification has no recovery flow — high priority

Evidence: `data/Sources.kt`, `WebSource.document` detects a small set of HTML challenge markers and otherwise throws a generic HTTP error. The shared HTTP client has no persistent source cookie/session integration; there is no verification WebView. Opening the site externally does not give the native HTTP client the browser's session.

Fix: typed source failures (verification required, rate limited, offline, unavailable, parser changed), a source-status panel, and a user-driven verification screen for compatible sources. Pause that source's requests while verification is pending, retain queued work, and retry one original request after verification. Do not let automatic image retries repeatedly hit a challenge.

Acceptance: ordinary 403, 429, DNS failures and challenge HTML produce different actions; successful verification resumes the original operation; expired sessions prompt again without losing downloads. See the proposed design below.

### 2. Damaged downloaded images cannot be repaired by Retry — high priority

Evidence: `ui/ReaderViewModel.kt`, `pageFileFor` returns any existing downloaded file before checking cache/network. `invalidateCachedPage` deletes only the cache file and manifest. `data/Downloads.kt` also skips existing page files without validating them. A corrupted local page therefore remains the first choice on every reader retry.

Fix: validate local pages on decode failure, identify the affected download as needing repair, and offer Repair page / Repair chapter. Fetch to a temporary file, validate, then replace atomically. Retain all other pages and reading progress. When offline, report that repair requires a connection instead of counting down doomed retries.

Acceptance: deliberately truncate one saved page; repair only that page online; other local pages remain readable offline. A completed download with missing files must not remain misleadingly marked fully available.

### 3. Cancellation does not cancel active HTTP calls — high priority

Evidence: `Downloads.kt` and `ReaderViewModel.pageFileFor` use blocking OkHttp `execute()` and `copyTo` without binding coroutine cancellation to `Call.cancel()`. Download cancellation is checked between images, not during copying. A reader image fetch also holds a shared mutex, so a canceled slow request can hold up the replacement request until it ends or times out.

Impact: pause, chapter switching and delete can feel unresponsive; cancellation/deletion races require testing. A WorkManager cancellation acknowledgement should not be treated as proof that blocking file I/O has stopped.

Fix: a cancellable HTTP helper, cancellation-aware streaming, and per-chapter coordination for writes/deletion. Check active worker ownership before publishing progress/completion. Cancel the actual call promptly and prevent an old worker from overwriting Paused/Deleted state.

Acceptance: pause/delete during a deliberately slow response, rapidly switch chapters, and lose connectivity mid-image. No late Complete state, orphan files, or blocked reader fetches.

### 4. Image downloads are not bounded by size — high priority for low-storage phones

Evidence: both reader/download image paths stream to disk without a byte ceiling. Download storage is checked before a page, and the reader cache is trimmed only after a page is saved. The current target is exempt from eviction, so a single file can exceed the nominal 128 MB cache budget. HTML responses are also read fully into strings.

Fix: configurable sensible per-image and HTML-response limits, streamed byte accounting, free-space checks during large transfers, and image validation before cache promotion. Explain oversized/unsupported pages separately from network failures.

Acceptance: an oversized or endless response stops cleanly, removes its partial file and leaves existing downloads intact.

### 5. No user-controlled backup or restore — high priority

Evidence: Android backup is disabled in the manifest and the app has no export/import flow. Library, follows, preferences and progress exist only in the local database/settings.

Fix: versioned metadata backup through Android's document picker; include Library, progress, follows, title settings and source order. Exclude image files and session cookies by default. Preview restore counts and validate the archive before a transactional import. Optional scheduled backup can follow manual export/restore.

Acceptance: round-trip into a clean installation, preserve existing data on invalid input, and define merge behavior for duplicate titles and progress.

### 6. Bulk-download preview can become stale — medium priority

Evidence: `ui/KomoriScreen.kt:1363` memoizes candidates by choice, downloads and progress only. Candidate selection also depends on chapters, title preferences and settings, which are absent from those keys/subscriptions. A feed refresh while the dialog is open can leave the displayed count and selected batch based on the old feed.

Fix: derive candidates from an explicit immutable state containing every input; revalidate the chosen policy against the current feed when Queue is pressed. Make the dialog scrollable, use at least 48 dp selectable rows and expose radio selection semantics.

Acceptance: refresh from a short cached list to a full list while the dialog is open; count updates and Queue uses the latest language/group policy. Test small screens, landscape, large fonts and TalkBack.

### 7. Continuous scrolling is currently forward-oriented — medium priority

Evidence: `WebtoonReader.kt` drops older chapters from its bounded window and only appends next chapters. It has no corresponding prepend/previous-chapter loader. After several transitions, scrolling back reaches the retained window boundary. Its next-load effect also does not key on a changed next-chapter identity; a feed change after the effect has returned needs a regression test.

Fix: retain the bounded window but reload older neighbors on demand with stable scroll anchoring. Key loading on neighbor identity and relevant feed/preferences. Add a small chapter transition marker and chapter-jump control.

Acceptance: scroll forward five chapters, backward four, then rotate and relaunch; verify position and completion remain correct. Refresh a feed that introduces a next chapter while the reader is open.

### 8. Retry policy does not distinguish failure types — medium priority

Evidence: `ImageRetry.kt` retries based only on a failed Boolean and delay. It does not know whether the cause is no network, a challenge, 429, deleted content or corrupt bytes. Attempts are tied to composition lifetime, so leaving/re-entering an item can reset its budget.

Fix: explicit failure categories; resume on connectivity for offline failures, respect Retry-After for throttling, require verification for challenges, repair corrupt files, and avoid automatic retries for permanent missing pages. Keep a page-level attempt budget outside disposable UI composition.

Acceptance: deterministic fake-clock/network tests plus real interruption tests. Do not promise automatic recovery from source access restrictions.

### 9. Network errors incorrectly name MangaDex — medium priority

Evidence: `data/ConnectionErrors.kt:9` and `:11` hard-code MangaDex for SSL/DNS failures although this helper serves every source and download worker.

Fix: pass source context or use a source-neutral message. Provide a redacted diagnostics panel with source, operation, HTTP status and time. Never log session cookies or authorization values.

### 10. Download queue needs durable ordering and clearer waiting states — medium priority

Evidence: downloads are individual WorkManager jobs serialized by a process mutex; database Download rows have no queue index or priority. The interface cannot distinguish waiting for Wi-Fi/storage from waiting behind another chapter, and has no reorder/cancel-selected action.

Fix: persist queue position and use a controlled dispatcher; keep concurrency low by default. Show Waiting for Wi-Fi, Waiting for storage, Paused and Verification required. Add grouped-by-title display, selected-item actions, size totals and optional notification controls. Reconcile UI state with WorkManager after process death.

Acceptance: hundreds of queued chapters, restart, battery restrictions, Wi-Fi loss and storage pressure; queue order and completed pages survive.

### 11. Large-library performance has avoidable costs — medium priority

Evidence: `Database.kt` exposes whole-table flows for manga/progress/downloads. `ReaderViewModel` eagerly observes them. Library rendering repeatedly finds manga/shelf entries in lists. Progress writes invalidate the full progress query.

Fix: indexed joins/projections, maps for lookup and title-scoped progress queries; introduce paging when benchmark data warrants it. Keep the existing tiled image decoder and bounded reader window. Benchmark before increasing parallel downloads or preloading.

Acceptance: 1,000 saved titles and 50,000 progress entries on a physical 2 GB device; measure startup, scrolling, memory peak and battery use. Current emulator evidence is not sufficient for a performance guarantee.

### 12. Update and release quality can improve — lower priority

Existing strengths: strict update package/version checks, SHA-256 validation, matching installed signer, signed releases and upgrade preservation tests. Keep these.

Improvements: Stable/Preview channel choice, release notes, persistent snooze, conditional GitHub requests and longer foreground cooldown. Current checks include prereleases and can repeat after a 30-second foreground interval. CI runs unit tests/lint/build but does not run Android instrumentation. Add emulator migration/reader tests to release gating and publish a short feature-oriented changelog.

## Product and visual improvements

Recommended after the reliability work:

- Library: custom categories, unread badges, status filters, multi-select, mark read/unread and a new-chapter Updates feed. Schedule refresh conservatively and let users choose which titles participate.
- Sources: enable/disable sources, drag reordering, capabilities and connection status, per-source settings and a clear experimental/unavailable label. Hide unsupported filter controls rather than offering actions that cannot work.
- Reader: page/chapter jump sheet, slider, brightness/dimming, rotation lock, optional volume-key navigation and webtoon zoom. Preserve per-title choices. Paged mode should support moving into the previous chapter from its first page.
- Downloads: compact title groups, bytes/storage usage, selected/range downloads, delete-read actions with preview, and optional automatic deletion only after explicit opt-in.
- Duplicate management: show source badges and alternate-title matches; offer a reviewed migration flow carrying progress between editions. Never silently merge by title alone.
- Appearance: retain the jade palette, improve hierarchy and density choices, support system/light/dark theme, use source badges and restrained unread indicators, and supply cover error placeholders. Split the long Settings page into Reader, Library, Downloads, Sources and Updates.
- Accessibility: verify large fonts, landscape, 48 dp controls, selected-state announcements, contrast and RTL layouts. Current passing lint is not an accessibility audit.

## Browser verification: proposed approach

1. **Recognize the problem accurately.** Check `cf-mitigated: challenge` for Cloudflare Challenge Pages, then use carefully scoped HTML checks for other providers. Do not classify every 403 as verification. Cloudflare documents that its challenge responses are HTML even when an image/API response was requested: https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/
2. **Offer a user-controlled Verify source action.** A compatible source can use a temporary in-app WebView with JavaScript, DOM storage and cookie support. Show the real source domain. Keep the user in control of the challenge, restrict navigation to the source and required challenge services, expose no native JavaScript bridge and never ignore TLS errors. Do not instantiate a browser on every launch or during normal native reading.
3. **Manage sessions deliberately.** Use Android CookieManager with a carefully scoped native HTTP cookie adapter where the source permits it. Respect domain/path/secure/expiry rules, synchronize Set-Cookie updates and retain a consistent session user agent. Never forward source cookies to arbitrary image/CDN hosts. Provide Clear source session and keep sessions out of backups/logs. Android reference: https://developer.android.com/reference/android/webkit/CookieManager
4. **Verify success by retrying the original request once.** Page-load completion or the presence of a cookie is not proof that the native client has access. Keep the queue paused if access is still blocked. Cookie sharing is not a universal solution: browser and network checks can still reject native requests.
5. **Provide a full-browser fallback honestly.** Custom Tabs use the preferred browser's state; they do not make its cookies available to Komori's OkHttp client. This is useful for opening the site and diagnosing compatibility, but cannot promise to unlock native downloads. Chrome's documentation explains browser-state sharing and WebView separation: https://developer.chrome.com/docs/android/custom-tabs
6. **Prefer site-supported access.** If a source will not support embedded verification or native requests, seek an official API/integration or retain browser access and clearly label native support unavailable. Comix currently has an explicitly unimplemented adapter; solving a browser challenge alone would not implement its catalog/chapter/page parsing.

Cloudflare explicitly describes limited WebView support and does not support automated browsers for production challenge solving. Do not build CAPTCHA automation, user-agent rotation or repeated challenge retries: https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/

For user-facing troubleshooting: update Chrome and Android System WebView; ensure JavaScript/cookies work; test with a stable connection; temporarily disable interfering VPN/content blockers; try another normal browser/network; if still blocked, provide the site's error/Ray ID to its administrator. Avoid changing networks during a verification attempt. Official guidance: https://developers.cloudflare.com/cloudflare-challenges/troubleshooting/challenge-solve-issues/

## Suggested delivery order

1. Reliability patch: cancellable HTTP, page repair, transfer limits, accurate errors, reactive bulk counts and failure-specific retries, with regression tests.
2. Source access: verification/session flow for supported general sources, status UI, paused queue recovery and real-device verification tests.
3. Data protection and queue: backup/restore, storage management, durable queue ordering and process-death tests.
4. Reader/Library polish: backward continuous chapters, chapter jumps, categories, unread badges, settings organization and accessibility checks.

Release gates should include Android 8/API 26 minimum support, Android 16/API 36 behavior, a physical low-memory phone, offline cold launches, mid-download cancellation, nearly-full storage, corrupted pages, and upgrades preserving all saved state.
